# 과거 자리 기록 입력 우선순위 및 가상 시뮬레이션

작성일: 2026-09-01
관련 기록: `09-work-progress.md`

## 1. 확인된 요구사항

- 현재는 2학기다.
- 1학기 자리배치는 3월부터 7월까지 총 5회 변경되었다.
- 각 과거 기록은 학생 이름과 자리 번호로 구성된다.
- 과거 자리 번호는 현재 테스트 교실의 자리 번호와 일치한다.
- 실제 데이터를 입력하기 전, 전체 흐름을 가상으로 검증해야 한다.

## 2. 우선순위

| 우선순위 | 범위 | 완료 조건 |
|---|---|---|
| P0 | 5회 기록 입력·매칭 | 학생 이름→현재 studentId, 자리 번호→현재 seatId 매칭 |
| P0 | 입력 검증 | 중복 이름, 미등록 학생, 없는 자리, 한 회차 내 중복 배정 차단 |
| P0 | 회차 저장 | 1학기 1~5회차를 각각 확정 이력으로 저장 |
| P1 | 미리보기 | 저장 전 회차별 오류와 매칭 결과 확인 |
| P1 | 추천·통계 연계 | 2학기 추천과 학생별 자리 경험에 1학기 5회 반영 |
| P2 | 편의 기능 | 붙여넣기, 행 수정, 일괄 저장, 정확한 날짜 입력 |
| P3 | 기록 화면 개선 | 학기·회차·날짜 필터 및 요약 표시 |

## 3. 가상 데이터 흐름

실제 DB에는 저장하지 않고 다음 순서만 검증한다.

1. 1차부터 5차까지 각 회차에 학생 이름과 현재 교실의 자리 번호를 입력한다.
2. 학생 이름을 현재 학생 명단의 `studentId`로 매칭한다.
3. 자리 번호를 현재 layout의 `seatId`로 매칭한다.
4. 각 회차가 학생·자리 중복 없이 완성되는지 검증한다.
5. 각 회차를 `semester=1`인 독립적인 `SeatingSession`으로 저장한다고 가정한다.
6. 2학기 추천은 이 5개 session을 과거 이력으로 읽고, 2학기 새 기록은 별도 회차로 저장한다고 가정한다.

## 4. 가상 시뮬레이션 판정

- 입력 회차: 5개
- 학기: 모두 1학기
- 회차: 1, 2, 3, 4, 5
- 기간: 3월~7월
- 자리 매칭: 현재 자리번호와 일치한다는 전제
- 기존 snapshot: 변경하지 않음
- 기대 결과: 1학기 5회가 추천 이력과 학생별 경험 통계에 반영됨

### 통과 조건

- 모든 학생 이름이 정확히 하나의 현재 학생과 연결된다.
- 모든 자리 번호가 현재 교실에 존재한다.
- 한 회차에서 학생과 자리가 중복되지 않는다.
- 5개 회차가 서로 덮어쓰지 않고 독립적으로 보존된다.
- 날짜가 불명확한 회차는 임의 날짜로 확정하지 않는다.
- 2학기 추천은 1학기 이력을 읽지만 1학기 기록을 수정하지 않는다.

## 5. 구현 순서

1. P0 입력 형식과 매칭 검증
2. P0 5회차 미리보기 및 저장 transaction
3. P1 기록·통계·추천 연계
4. P2 입력 편의 기능
5. P3 기록 화면 필터와 요약

현재 단계는 실제 파일 입력이나 코드 변경이 아닌 요구사항 우선순위와 가상 흐름 검증 단계다.

## 8. 3단계 P1 진행 결과: 이력·통계·추천 연계 점검

### 현재 구조에서 확인한 연계 지점

- 학생별 경험 통계는 확정된 모든 자리 assignment snapshot을 집계한다.
- 자동 추천은 확정된 session 목록을 받아 동일 자리, 인접 관계, 위치 경험을 계산한다.
- 현재 자리 표시는 가장 최근 확정 session의 assignment를 사용한다.

### 가상 입력 후 기대 흐름

| 단계 | 입력 상태 | 기대 결과 |
|---|---|---|
| A | 1학기 1~5회 저장 | 학생별 자리 경험에 5회 누적 |
| B | 2학기 첫 배치 후보 생성 | 1학기 5회 이력을 과거 경험으로 사용 |
| C | 2학기 1회 확정 | 최신 자리 표시는 2학기 1회 결과 |
| D | 2학기 두 번째 후보 생성 | 1학기 5회 + 2학기 1회 이력 사용 |
| E | 자리 기록 조회 | 학기·날짜·회차별로 6개 이상 기록 구분 |

### 현재 구현에서 확인된 P1 위험 지점

- `confirmedSessions`와 `latestAssignments`가 회차 번호만으로 정렬되면, 학기별 회차가 1부터 다시 시작할 때 최신 기록을 잘못 선택할 수 있다.
- 과거 1학기 5회와 2학기 기록을 날짜 순서로 정렬해야 time-decay와 최신 자리 표시가 올바르게 동작한다.
- 기록 목록에는 학기 필드가 필요하며, 동일 날짜·동일 학기·동일 회차 중복 여부도 저장 전에 확인해야 한다.
- 학생별 통계는 1학기 기록을 포함하되, 1학기와 2학기를 분리해 확인할 수 있는 조회 기준이 필요하다.

### 3단계 판정

- 이력 보존: 구조상 가능하나 학기별 회차 정렬 보완 필요
- 추천 반영: 과거 session 전체를 사용하도록 설계되어 있어 1학기 5회 반영 가능
- 최신 자리 표시: 학기별 회차 재시작을 고려한 날짜 정렬 검증 필요
- 학생별 통계: snapshot 기반 누적 가능, 학기 필터는 추가 요구사항
- 실제 저장: 아직 실행하지 않음

다음 단계는 위 P1 위험 지점을 해결하는 정렬·최신 기록·통계 조회 설계다.

## 9. 4단계 P1 진행 결과: 정렬·최신 기록·통계 기준

### 확정 정렬 규칙

- 자리 기록 목록: `occurredOn DESC` → `createdAt DESC` → `sequenceNo DESC`
- 추천 엔진 이력: `occurredOn ASC` → `createdAt ASC` → `sequenceNo ASC`
- 현재 자리 표시: 가장 최근 `occurredOn`의 확정 session
- 같은 배치일이 여러 개면 실제 저장 시각을 보조 기준으로 사용한다.
- 회차 번호만으로 최신 여부를 판단하지 않는다.

### 학기 처리 규칙

- 1학기와 2학기의 회차 번호는 각각 1부터 시작할 수 있다.
- 추천 이력은 기본적으로 학기와 관계없이 같은 학년도 전체 확정 기록을 날짜 순서로 사용한다.
- 기록 화면은 전체 보기와 1학기/2학기 필터를 제공한다.
- 학생별 경험 통계도 전체 보기와 학기별 보기를 구분한다.

### 가상 정렬 결과

| 기록 | 학기 | 회차 | 배치일 | 최신 순위 |
|---|---:|---:|---|---:|
| 1학기 1차 | 1 | 1 | 3월 | 7 |
| 1학기 2차 | 1 | 2 | 4월 | 6 |
| 1학기 3차 | 1 | 3 | 5월 | 5 |
| 1학기 4차 | 1 | 4 | 6월 | 4 |
| 1학기 5차 | 1 | 5 | 7월 | 3 |
| 2학기 1차 | 2 | 1 | 9월 | 2 |
| 2학기 2차 | 2 | 2 | 10월 | 1 |

이 정렬에서는 2학기 1차가 회차 번호 1이어도 1학기 5차보다 최신으로 판정된다.

### 4단계 판정

- 회차 재시작 문제: 날짜 우선 정렬로 해결 기준 확정
- 최신 자리 표시: 날짜와 저장 시각 기준으로 판정
- 추천 time-decay: 오래된 1학기 기록부터 최신 2학기 기록 순서로 전달
- 통계 조회: 전체/학기별 필터 기준 확정
- 실제 DB 쿼리 수정: 아직 실행하지 않음

다음 단계는 P2 입력 편의 기능 전에, P1 정렬 기준을 적용할 구현 항목과 회귀 테스트 목록을 확정하는 것이다.

## 6. 1단계 P0 진행 결과: 입력·매칭 검증

### 권장 입력 형식

회차별로 다음 TSV 형식을 사용한다.

```text
학생이름<TAB>자리번호
김하늘<TAB>seat-01
이도윤<TAB>seat-02
```

- 한 회차당 한 블록으로 입력한다.
- 첫 줄은 선택적으로 `학생이름\t자리번호` 헤더로 둔다.
- 자리번호는 현재 교실에서 사용하는 자리번호를 그대로 사용한다.
- 5회차를 구분하기 위해 회차별 블록 또는 파일을 사용한다.

### 매칭 규칙

1. 이름을 현재 학년도 학생 명단에서 검색한다.
2. 정확히 한 명이면 현재 `studentId`로 변환한다.
3. 0명이면 미등록 학생 오류다.
4. 2명 이상이면 동명이인 확인 오류다.
5. 자리번호를 현재 layout의 `seatCode` 또는 자리 ID와 비교한다.
6. 자리번호가 없으면 존재하지 않는 자리 오류다.
7. 같은 회차에서 학생 또는 자리가 반복되면 중복 배정 오류다.

### 가상 검증 예시

| 입력 | 판정 | 처리 |
|---|---|---|
| 등록 학생 + 현재 자리번호 | 통과 | studentId·seatId로 변환 |
| 미등록 학생 이름 | 실패 | 해당 행 수정 요구 |
| 동명이인 이름 | 실패 | 학생번호 등 추가 식별 정보 요구 |
| 현재 layout에 없는 자리번호 | 실패 | 자리번호 수정 요구 |
| 한 회차에서 같은 학생 2회 | 실패 | 중복 학생 오류 |
| 한 회차에서 같은 자리 2회 | 실패 | 중복 자리 오류 |

### 1단계 시뮬레이션 판정

- 입력 포맷: 확정
- 학생 연결 키: 이름 검색 후 `studentId` 저장
- 자리 연결 키: 현재 자리번호 검색 후 `seatId` 저장
- 5회차 처리: 회차별 독립 검증
- 실제 저장: 아직 실행하지 않음
- 보류 사유: 실제 학생 이름·자리번호 데이터와 정확한 날짜가 필요함

다음 단계는 P0의 5회차 미리보기와 저장 transaction 설계다.

## 7. 2단계 P0 진행 결과: 5회차 미리보기·저장 transaction

### 미리보기 화면 구성

- 상단에 `1학기 · 5회차`와 각 회차의 배치일 상태를 표시한다.
- 회차별로 입력 행 수, 매칭 성공 수, 오류 수를 표시한다.
- 각 행에 원본 학생 이름·자리번호와 변환된 `studentId`·`seatId`를 함께 표시한다.
- 오류가 있는 회차는 저장 버튼을 비활성화한다.
- 날짜가 확정되지 않은 회차는 `날짜 확인 필요` 상태로 표시하고 저장하지 않는다.

### 저장 transaction 규칙

1. 5개 회차 전체의 검증을 먼저 완료한다.
2. 모든 회차가 통과한 경우에만 하나의 transaction을 시작한다.
3. 회차 순서대로 1학기 `SeatingSession` 5개와 각 assignment를 저장한다.
4. 하나라도 저장에 실패하면 전체 transaction을 rollback한다.
5. 부분 저장된 1~4회차를 남기지 않는다.
6. 저장 완료 후 기록 화면과 추천 이력이 5개 회차를 모두 조회하는지 확인한다.

### 가상 transaction 시나리오

| 시나리오 | 1~5회차 검증 | 기대 결과 |
|---|---|---|
| 정상 입력 | 모두 통과 | 5개 session 일괄 저장 |
| 3회차에 없는 자리번호 | 3회차 실패 | 저장 전 차단, DB 변경 없음 |
| 5회차에 동명이인 | 5회차 실패 | 해당 행 수정 후 재검증 |
| 저장 중 DB 오류 | 사전 검증 통과 | 전체 rollback, 부분 기록 없음 |
| 날짜 미확정 | 날짜 상태 오류 | 날짜 확인 전 저장 불가 |

### 2단계 판정

- 미리보기: 회차·행·매칭 결과·오류를 확인할 수 있도록 정의함
- 저장 단위: 5회차 전체를 하나의 transaction으로 처리
- 실패 처리: 부분 저장 없이 전체 rollback
- 실제 저장: 아직 실행하지 않음
- 다음 단계: P1 이력·통계·추천 연계 검증
